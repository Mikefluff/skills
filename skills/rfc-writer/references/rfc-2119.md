# RFC 2119 keywords

When an RFC / spec contains a **normative requirement** — something the implementation MUST follow — use the RFC 2119 keywords. They have precise meaning agreed upon by the engineering community.

Reference: [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) (1997) + [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) (2017 — clarifies that ONLY uppercase keywords have RFC 2119 meaning).

---

## The keywords (UPPERCASE = normative)

| Keyword | Meaning |
|---|---|
| **MUST** / **SHALL** / **REQUIRED** | Absolute requirement. Implementations that don't follow this are non-compliant. |
| **MUST NOT** / **SHALL NOT** | Absolute prohibition. |
| **SHOULD** / **RECOMMENDED** | Strong preference. Implementations may deviate, but must understand the full consequences. |
| **SHOULD NOT** / **NOT RECOMMENDED** | Strong preference against. |
| **MAY** / **OPTIONAL** | Truly optional. Different implementations may or may not implement; both are valid. |

### The capitalization rule

**Only the UPPERCASE form has RFC 2119 meaning.** Lowercase "should" / "must" / "may" are normal English words with normal English meaning.

✅ "Clients MUST send the `Authorization` header" → normative requirement
✅ "Clients should consider rate-limiting their requests" → suggestion / informal guidance (lowercase)

This distinction matters in long docs where some statements are formal requirements and others are informal observations.

---

## When to use each

### MUST / MUST NOT

**Use when** non-compliance breaks interoperability, security, or correctness.

Examples:
- "Clients MUST send the `Authorization` header on every request to authenticated endpoints"
- "The server MUST reject requests with `Content-Length` larger than 10 MB"
- "Implementations MUST NOT log password values"
- "Tokens MUST NOT be reused across services"

### SHOULD / SHOULD NOT

**Use when** there's a strong preference but legitimate reasons may exist to deviate.

Examples:
- "Clients SHOULD implement exponential backoff on 5xx responses" (other backoff schemes are acceptable)
- "Servers SHOULD include a `Retry-After` header on 429 responses" (clients can also use a default)
- "Clients SHOULD NOT include sensitive data in URL query parameters" (querystring logging is the concern; HTTPS mitigates somewhat)

### MAY / OPTIONAL

**Use when** the feature is truly optional and interoperability isn't affected.

Examples:
- "Clients MAY include a `X-Request-ID` header for traceability"
- "Servers MAY return cached responses from `GET` requests"
- "Implementations MAY support gzip compression (per RFC 1952)"

---

## When NOT to use the keywords

❌ In casual / non-normative prose:
> "We MUST consider performance" — that's not a real "MUST"; the user is just emphasizing. Use "must" lowercase or rewrite.

❌ In documentation of optional features:
> "You MUST enable feature flag X to use this" — flag enabling is the user's choice; this is documentation, not a normative requirement on the implementation. Use lowercase.

❌ When the meaning is ambiguous:
> "Clients SHOULD authenticate" — does it mean "we strongly recommend"? Or "they have to"? Pick MUST or "we recommend" (lowercase). Don't dance around.

## Common normative statement structures

### Required behavior

```
{Actor} MUST {action} {when conditions}.
```

Examples:
- "Clients MUST send the `Authorization` header when calling authenticated endpoints"
- "Servers MUST reject expired tokens with HTTP 401"
- "Implementations MUST treat unrecognized fields as opaque (preserve on read, do not modify, propagate on write)"

### Forbidden behavior

```
{Actor} MUST NOT {action} {when conditions}.
```

Examples:
- "Clients MUST NOT include the access token in URL query parameters"
- "Servers MUST NOT respond with `Authorization-Required` for endpoints in the `/public` namespace"

### Recommended behavior

```
{Actor} SHOULD {action} {when conditions}.
{Actor} SHOULD {action} {when conditions}. Implementations that do not {action} MUST {alternative}.
```

The second form is useful when SHOULD is non-trivial — it spells out what's required if the recommendation isn't followed.

Examples:
- "Servers SHOULD include the `Retry-After` header on 429 responses"
- "Clients SHOULD implement exponential backoff. Clients that do not implement exponential backoff MUST limit retries to 3 attempts and document this behavior."

### Optional behavior

```
{Actor} MAY {action} {when conditions}.
```

Examples:
- "Clients MAY cache responses for up to the duration specified in `Cache-Control`"
- "Implementations MAY include vendor-specific extension fields"

## A concrete example block

In an RFC, the normative section might look like this:

```markdown
## Authentication

All authenticated endpoints require a Bearer token.

### Requirements

1. Clients MUST send the `Authorization: Bearer {token}` header on every request to
   endpoints under `/api/v2/private/`.
2. Tokens MUST be obtained via the OAuth 2.0 client credentials grant
   (see RFC 6749 §4.4).
3. Tokens MUST be transmitted over HTTPS. Servers MUST reject any request to a
   private endpoint received over plain HTTP with HTTP 426 Upgrade Required.
4. Tokens MUST NOT be included in URL query parameters or path segments.
5. Clients SHOULD cache valid tokens and reuse them until 60 seconds before expiry
   to reduce auth-service load.
6. Servers SHOULD include a `WWW-Authenticate` header on 401 responses
   indicating the supported authentication schemes.
7. Clients MAY include a `X-Request-ID` header for traceability.
```

The capitalization makes the spec immediately scannable by readers looking for the
"must" requirements.

## Combining with lowercase prose

Most of an RFC is non-normative prose. The 2119 keywords appear in the **Detailed
proposal** section where requirements are specified.

✅ Good:
```
## Motivation

The current authentication scheme requires a callback to the auth service on every
request. We should reduce this latency.   ← lowercase "should" — informal

## Detailed proposal

### Authentication requirements

Clients MUST send the `Authorization` header on every authenticated request.   ← normative
Servers MUST validate the token's signature before processing the request.   ← normative
Servers SHOULD cache the public key for 24 hours and refresh daily.   ← preferred
```

❌ Bad:
```
The auth service MUST be improved. Clients MUST be happier with the system.
```

This is informal language using uppercase. Confuses readers about what's actually
required.

## The "Conventions" section

Many RFCs include a "Conventions" section at the top that explicitly states the
keywords' meaning. Use this template:

```markdown
## Conventions used in this document

The keywords "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in BCP 14
([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119),
[RFC 8174](https://www.rfc-editor.org/rfc/rfc8174))
when, and only when, they appear in all capitals, as shown here.
```

Including this section makes the spec rigor explicit and signals the author
understands RFC conventions.

---

## Quick checklist before publishing

- [ ] Every uppercase MUST / SHOULD / MAY is a genuine normative requirement
- [ ] No casual uppercase MUST in motivation / discussion sections
- [ ] Lowercase "should" / "must" / "may" used for informal preferences
- [ ] Conventions section included at the top of the spec
- [ ] If using MUST without obvious rationale, the rationale is given nearby
- [ ] If using SHOULD, what happens if implementations deviate is clear
- [ ] No "MUST OR SHOULD" / "MUST CONSIDER" / other novel formulations
